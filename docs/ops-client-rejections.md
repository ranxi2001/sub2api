# 用户侧拒绝与渠道故障

请求模型不在所选分组的能力范围内，以及本站用户余额不足，属于用户侧业务拒绝。HTTP 状态与响应正文保持原样（模型不支持为 404，余额不足为 403）；记录继续保存在 `ops_error_logs`，不因隔离而丢弃排查证据。

新记录使用 `error_owner=client`、`error_source=client_request`、`error_phase=request`、`is_business_limited=true`。本地余额不足在日志中归为 `billing_error`；本地模型不支持保持 `model_not_found`，用户错误请求页归为参数/请求错误。请求侧拒绝不关联上游账号、模型或端点，避免等待后计费复检把先前选中的账号算作故障账号。

运维默认错误列表、SLA 与错误率告警沿用业务排除标记。管理员可在错误明细选择“排除项”，并以责任方“客户端”筛选；“全部”及用户自己的错误请求记录仍可查询。用户原始请求失败总量不是平台故障数，不应将其直接用作系统故障率。

渠道监控 V2 的事实聚合、历史汇总和错误明细同步排除这些用户侧业务拒绝；V3 复用 V2 聚合数据，因此采用相同口径。排除发生在请求去重之后，避免最新结果已是用户拒绝，却重新计入同一请求较早的上游尝试。账号池整体限流仍为渠道容量问题，不随用户侧业务拒绝一起过滤。

供应商账号余额不足、无法明确识别的模型或参数错误，以及没有明确请求拒绝证据的上游错误仍保留为渠道问题。不能只根据 HTTP 403、404 或“余额不足”文字过滤。

## 上下文超限被包装为 502

部分 Responses 供应商将 `response.failed` 中的 `context_length_exceeded` 包装为 HTTP 502。最终请求失败、有效上游状态为 502，且当前错误消息或上游详情含明确的 `context_length_exceeded` 错误码时，按 `client/request/context_limit` 归类并进入排除项；保留客户端及上游的原始 HTTP 状态、错误来源、消息和详情。没有单独上游状态时使用最终 HTTP 状态。新日志写入与历史日志查询采用相同规则，Ops SLA、趋势、小时聚合及 V2/V3 渠道聚合共用此排除判定。

502 中只有 `prompt is too long`、`Request payload is too large` 或普通 Bad Gateway 等文字时不自动排除；有效上游状态为 429/503、鉴权阶段、最终已恢复的请求，以及只在更早尝试出现的上下文错误码不由这条规则改判。原有 400/413/422 的明确上下文拒绝判定保持不变。

这里修正的是错误分类和监控口径，不会自动压缩上下文、改变供应商窗口、改写 HTTP 响应或改变重试策略。请求实际超限仍需调用方压缩历史或使用已核实支持对应上下文长度的模型线路；被映射到较小窗口等供应商能力问题仍需另行排查。

## 旧数据与部署边界

没有数据库迁移，也不删除或批量重写历史日志。渠道聚合兼容旧的 `routing/model_not_found/platform` 本地模型拒绝记录，以及旧的 `request/api_error/client` 用户余额不足记录；要求已有业务排除标记，并检查上游证据。

新代码生效后，后续聚合与现有近期重算窗口使用新口径。已经保存的较早 V2/V3 汇总不会仅因换二进制全部重建；如需统一历史看板，需要另外安排对应时间段的 `RecomputeRange` 重算，不能将尚未重算的旧汇总宣称已修复。旧日志原有责任方和类型不会被回写。回退代码会恢复旧聚合规则，不需要回滚 schema。

本变更没有主动调用供应商、重启服务或执行生产数据重算。UI 组件和接口响应结构不变。
