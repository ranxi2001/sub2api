# 优先调度

入口：**智能运维 → 优先调度**（`/admin/priority-scheduling`）。默认关闭。设置保存在 `priority_scheduling_v1`，无需数据库迁移。

## 候选分析与实时数据

候选评分按所选模型、分组和时间窗口读取历史，返回 `selection_policy=read_only_analysis`。此入口不采集实时并发或当前实例的 HTTP 尝试证据。历史质量、延迟和财务依据充分，且唯一缺项为实时并发时，页面显示“历史指标达标”；真正缺少质量、延迟或利润样本时仍显示“历史数据不足”，已知超标显示“历史指标未达标”，延迟惩罚到期但仍超目标时显示“延迟恢复期”。这些状态不表示账号当前可调度，也不改写 API 的原始 `tier`、得分或实际选号逻辑。

历史分析的并发与上游尝试错误率显示“未采集”，不展示默认零时间、0 分钟错误窗口或 1.000 错误乘数。得分仍使用中性并发值 `0.5`，不应用实时错误惩罚；分流权重标为“估算分流权重”。有有效观察窗口但没有尝试的实际选号快照仍可显示“无尝试样本”，与未采集区分。

“重算最近实际选号”和会话粘性操作仍针对最近一次真实选号快照，其状态、容量和尝试证据保持原有口径。

## 生效范围

作用于 OpenAI 文本请求的自由选路，包括接入统一 OpenAI 调度器的兼容通道。可按分组 ID、公开请求模型名精确限定范围，留空表示不限。已有按路由模型填写的范围继续兼容，但统计仍按精确公开模型与分组分别读取，不合并别名。图片、视频及其他平台不启用此策略。

开启后，命中范围的请求使用高级调度器，优先利用较空闲的真实容量，容量接近时再按体验、优先级和权重分流。历史统计未就绪也继续均衡，不恢复固定 Top-K。关闭优先调度后恢复原调度开关控制。硬会话绑定、不可迁移的 previous_response_id、模型权限、账号状态、分组利润门槛、compact 能力、订阅优先分池和最终并发槽校验仍生效。**候选评分不是最终选择记录**；软粘性加分不参与本策略评分。

“在兼容的 BPS 与原生账号间均衡分流”对应 balance_protocols，默认开启；旧设置缺该字段时也使用此默认值，旧客户端保存时省略字段会保留当前值。开启后，不再仅因 BPS 池还有一个槽位就长期排除空闲的原生候选。仍按每个账号自身的协议发送，不自动开启 BPS，也不放开账号或分组模型限制。关闭此项可恢复 BPS 优先、原生兜底；图片、视频及不匹配优先调度范围的请求不受影响。

优先调度开启时，可迁移会话若存在利用率至少低 20 个百分点、每绑定分组的可用容量权重大于原账号两倍的兼容账号，可临时返回自由选号；保留原会话绑定，不迁移已发送请求，不改写已有响应或任务归属。健康且负载接近的会话继续复用原账号；读取实时负载失败时也保持原绑定。原有粘性逃逸开关继续控制该容量/EWMA 规则；独立的优先调度测量延迟惩罚按下文处理。

## OAuth 额度优先与 API Key 自动后备

在本页开启“优先消耗 OAuth 额度，末位 API Key 自动后备”。默认关闭；截止值默认是 **7d 已用 90%**，可设为 1–100。沿用本页分组和模型范围，不需要逐个指定 API Key。

开启后，在当前请求通过准入的同一候选池内：

1. OAuth 必须可调度、最新有效且完整的质量检测轮次通过、质量通过率达标，且没有已知延迟、拥堵、错误或亏损超标。延迟/利润样本不足本身不会阻止已有质量证据的新号参与。质量采用同请求模型的现有历史缓存，通常 30 秒刷新，最多使用 2 分钟内的缓存；最新明确失败取消本策略资格，即使历史平均仍达标。
2. 额度快照必须在 **5 分钟内**，不是未来时间，5h 和 7d 用量有效、重置时间仍在未来；7d 已用严格小于截止值，5h 未耗尽。未知、过期、刚重置但尚未刷新均不压制 API Key，不在请求线程发送探测。
3. 可承接槽位估算为 `ceil(实际并发上限 × 并发占用阈值 / 100) − 当前并发`，再受剩余 RPM 限制，并除以去重绑定分组数向下取整。排队、负载未知和无可用槽位的 OAuth 不提供退让预算。
4. 保持现有风险、容量档、体验档、优先级与加权抽样排序，从 **API Key 子序列的末尾** 逐个转为后备。每个 API Key 的剩余并发槽位消耗等量 OAuth 预算，预算用尽即停止；满载、排队或负载未知的 API Key 不消耗预算。例如 OAuth 共可承接 8 个槽位，末尾 API Key 各余 4 个槽位时，最后两个转后备。账号不能拆分，最后一个账号可能超过剩余预算；这不是吞吐承诺或独占容量预留。
5. 仅将合格 OAuth 移到这些后备 API Key 前面；其他低质量、慢或未知 OAuth 不因此插队。后备列表始终保留，抢槽竞争失败时同次选号即可继续使用 API Key。OAuth 容量减少时自然缩短后备尾部，排名较前的 API Key 先恢复；无合格 OAuth、额度达到截止值或关闭策略时，恢复原算法。OAuth 获得有效的新窗口快照后自动重新参与。

“后备”是一次选号的动态角色，**不写账号 status / schedulable**，不会误开启手动停用账号，也不需要后台恢复任务。新请求与已有允许故障转移的重试会重新计算；不新增已发送请求或已开始流的重试。API Key 在池内仍有排名，恢复时沿用算法顺序，不保存固定名单。

可迁移的 API Key 软会话若按相同策略落入后备，可返回自由选号；硬绑定、previous_response_id 和禁止粘性逃逸继续保留。BPS 优先、订阅优先、compact 能力的现有分池边界仍生效；不同分池的 OAuth 不会压制另一个池的 API Key。若开启独立“订阅优先”，它仍可能在本策略 90% 截止值以外优先使用订阅账号，本策略不会替它解除优先级。

页面增加开关、7d 截止值及“本次选号”角色标记。角色来自最近一次实际构造的调度顺序，是候选身份，**不是实际选中或持续停用记录**；刷新重算分数不会伪造一次新选号。旧配置缺字段默认关闭、阈值 90；旧客户端保存时省略字段会保留服务器当前配置。设置继续存入 `priority_scheduling_v1`，无数据库迁移；关闭开关即可退出本策略，回退旧二进制会忽略新字段。

本策略增加 OAuth 消耗机会，不保证失效前额度耗尽或利润提升。应按同分组、同模型观察 OAuth 消耗占比、失效时剩余额度、API 支出、首 Token 延迟和失败率。

## 账号字段管理

优先调度页面不提供按 Teams、Pro、Plus、API 类别批量生成排序的快捷设置。成本由账号成本倍率参与评分；账号优先级、并发数和负载因子仍可在账号管理中编辑。此前写入的账号字段保留原值；本策略的容量计算始终使用实际并发上限，不再让过大的负载因子掩盖占用。普通调度对负载因子的解释不变。同档需要共同参与分流的账号应设置相同优先级。

## 账号成本倍率

在**账号管理 → 新增 / 编辑账号**的计费字段旁设置“成本倍率”；批量编辑支持勾选后单独设置。默认 `0.1`，允许 `0`，最大 `1000000`。值保存在 `accounts.extra.cost_multiplier`，无需数据库迁移，现有账号未设置时也使用 `0.1`。导入、导出和账号复制随现有 extra 配置保留该值。

- 成本倍率用于优先调度的利润估算，与“账号计费倍率”和“分组计费倍率”独立；成功探测到有效上游 token 倍率后直接更新此字段，包含探测时的峰时倍率。下一次成功探测会再次更新；探测失败、过期或不支持时保留已保存的成本倍率，不恢复默认值。
- 例如成本倍率初始为 `0.1`，上游探测到 `0.14` 后，该字段保存并显示为 `0.14`，基础费用 `100` 的估算成本为 `14`。上游声明的 `0` 允许写入；非法值或超出字段范围的倍率不写入。
- 账号编辑中的“跟随上游”默认开启。关闭后，手填成本不会被后续探测覆盖，上游倍率和余额探测继续正常更新；重新开启后，下一次成功探测更新成本。开关保存在 `accounts.extra.cost_multiplier_auto_sync`，缺省或 `null` 表示开启。
- 充值赠送场景：充值金额能获得 5 倍额度，而上游报告倍率为 `1`，实际成本系数为 `1 ÷ 5 = 0.2`。关闭“跟随上游”，将成本倍率改为 `0.2` 并保存即可；账号列表上游探测列仍显示其报告的 `1.00x`。
- 手工修改成本倍率后立即用于后续评分；跟随开启时，下次成功探测会用上游倍率覆盖。未发生成功探测的账号继续使用手工值或默认 `0.1`。
- 估算成本＝同分组、同请求模型的 `SUM(COALESCE(account_stats_cost,total_cost)) × 当前账号成本倍率`。先聚合未乘倍率的基础费用，只乘一次成本倍率；即使账号计费倍率已是 `0.1`，也不会重复相乘。
- 修改后，在新请求生成候选快照时按当前倍率重估近期利润；历史使用日志、用户扣费和余额不被改写，账单里的历史账号成本列继续按原计费口径展示。
- 成本倍率必须同时保留在完整账号缓存和候选精简快照中，评分读取的是后者。修复旧版候选快照丢失该字段后，升级实例的启动重建会刷新缓存；手工编辑和成功探测也会更新这两份数据。页面“刷新评分”重新读取所选范围的历史分析；最近实际选号快照由新的自由选号请求生成。
- 所有账号统一按此字段估算，不再设置单号采购成本、人民币换算系数、回本窗口或按回本压力插队。旧配置中的 `teams` 对象和 `priority_teams_*` 元数据被忽略，保存新调度配置时不再带上 `teams`。
- 默认 `0.1` 是经营估算值，运营者应按各账号实际成本单独调整，不代表已核实采购价格或汇率。若仍使用独立的分组利润硬门槛，其既有账号计费倍率规则保持不变；本字段作用于本页优先调度评分。

## 数据与排序

1. **质量**：使用对应账号、同一模型的有效质量规则结果。只统计已完整保存的检测轮次；一轮中出现明确错误即失败，全部正确才算通过，网络失败等不确定轮次不计入分母。默认保留 24 小时；停用或修改规则后，旧结果不再参与。
2. **延迟**：默认统计近 60 分钟的流式首 token 延迟 P90，至少 5 个样本（同样作为利润样本下限）。按 `requested_model` 匹配，旧记录回退 `model`。排除缺失/非正首 token 时间及零 token、零费用的失败占位记录；免费但有真实 token 的请求可以参与。非流式总耗时不混作首 token 延迟。
3. **并发**：复用调度器实时并发占用及排队数据。占用达到阈值（默认 80%）或已有排队即标记拥堵。最终仍原子获取并发槽；竞争失败继续尝试后备账号。
4. **利润 / 成本**：按同分组、同模型的使用记录计算，用户扣费为 `SUM(actual_cost)`，估算成本按上节账号成本倍率计算。无首 token 或非流式记录仍参与财务统计。利润＝用户扣费−估算成本，利润率＝利润÷用户扣费；用户扣费为 0 时利润率为空。达到最少样本数后使用历史收益评分，出现亏损降为未达标。OAuth 数据不足时不推断利润；API 可以按独立成本倍率回退估算。不会修改用户扣费，也不保证历史收益等于下一笔收益。

5. **近期错误**：复用账号运行时错误率，超过 20% 降为体验未达标，同时对总分施加错误惩罚。错误 EWMA 除按请求更新外，还以 2 分钟半衰期衰减，避免账号少分到请求后只能靠新成功样本恢复。衰减适用于共用这份运行时统计的普通/优先调度，不改变真实限流、模型冷却或停用截止时间。首 Token 延迟不随空闲时间变小，也不会把空闲计为成功样本。这里不会从“费用为零”推断请求失败率。
   BPS 文本请求及其内联附件在获取托管代理时失败，仍返回原有 503 并记录诊断，但不计入账号错误率，也不作为成功样本消除已有惩罚。实际上游 429、503 及发送后的失败仍按原规则计入。此区分不会立即清空历史错误率或触发额外重试。

先分档再排序：

- 体验达标：有有效质量结果、足够延迟样本、已知负载和财务依据，且质量、延迟、并发均满足目标。
- 数据不足：不存在已知超标，但一项或多项数据缺失。
- 体验未达标：至少一项已知指标超标。

实际选择先区分已知质量不佳、近期错误偏高或历史亏损风险，再按当前预计占用划分容量档。当前并发和 RPM 占用取较大值，每 10 个百分点一档；下一次请求仍由原子并发获取和 RPM 准入校验处理，不会把所有空闲的小并发账号提前抬入下一档。缺少负载数据按未知档处理，真实排队排在无排队档之后。容量档相同时，才比较体验档、显式账号优先级和分流权重。因而容量接近时账号优先级有效；存在明显更空闲的安全候选时，较高优先级或略高利润不会持续覆盖容量差异。

例如同一风险档中，43% 占用、66.8 分的账号不会抢在 2% / 0% 占用的两个可用账号前面。全部账号都超过首 Token 目标时，仍区分负载和延迟，不把它们视为相同的“未达标”后仅按收益排序。保留所有后备候选；抢槽失败先尝试其他候选和新鲜负载，穷尽后才建立有界等待。订阅和 compact 能力分池继续生效；关闭跨协议均衡时 BPS 优先规则也继续生效。

对无已知超标、已有达标质量结果、负载已知且低于繁忙阈值、利润或延迟样本不足的 OAuth/API-key 账号，在有达标池时提供 10% 的探索概率；仅允许相同显式账号优先级、容量档不差于首选账号的候选。多个可探索账号共享这部分机会。未知质量、质量低于目标、近期错误、历史亏损、排队或冷却中的账号不能进入探索。它不是每 10 次请求必定一次的承诺，也不覆盖真实冷却或权限限制；没有达标池时，数据不足账号直接参与容量分流。

| 策略 | 质量 | 延迟 | 并发余量 | 成本 |
| --- | ---: | ---: | ---: | ---: |
| 体验优先 | 40 | 35 | 20 | 5 |
| 均衡 | 30 | 25 | 25 | 20 |
| 利润优先 | 20 | 15 | 20 | 45 |
| 自定义 | 用户配置 | 用户配置 | 用户配置 | 用户配置 |

各因子取 0–1：质量为通过率，延迟为 `1/(1+P90/目标)`，并发评分为 `(1-当前并发/实际并发上限)/(1+排队数)`（占用比例限制在 0–1）；拥堵分档也使用实际并发上限。财务因子为 `用户扣费/(用户扣费+理论成本)`（盈亏平衡取 0.5、零成本正收入取 1）；API 缺少财务样本时回退 `1/(1+倍率)`。缺失因子取中性值 0.5，OAuth 未知利润不按零收益评分；权重自动按总和归一化，最终乘 `1-近期错误率` 并换算成百分制。

### 分流权重与跨分组竞争

同容量档、同体验档和同优先级内的分流权重为：

```text
可用槽位 = max(0.05, 实际并发上限 - 当前并发) / (1 + 排队数)
评分偏好 = 0.5 + clamp(百分制评分 / 100, 0, 1)
额度偏好 = 0.5 + 0.5 × 有效额度余量
延迟因子 = max(0.02, 1 / (1 + (同模型 P90 / 首 Token 目标)^2))
OAuth 分流权重 = 可用槽位 × 评分偏好 × 额度偏好 × 延迟因子 / max(1, 绑定分组数)
```

延迟样本达到配置下限且 P90 为正时应用延迟因子，否则取 1，不把缺失时间当成零延迟样本。该体验约束在利润优先模式也有效，保留 0.02 下限供恢复及溢出使用。缺少实时负载时可用槽位取 1；满载账号的极小权重仅用于后备/排队顺序，实际抢槽仍跳过已知满载账号。额度偏好复用有效 7d 快照和现有 5h 低余量折扣，数据缺失、过期或窗口重置时取中性值 0.5。API-key 不应用分组数量除数。

绑定分组数由账号全部有效分组 ID 去重计算，不按分组名称、价格推断等级，也不划专属池。一个 OAuth 账号暴露给更多分组时，竞争来源更多；其他条件相同，当前请求更倾向绑定较少分组的账号。多分组账号始终保留正权重，其他候选不可用时仍可使用其容量，不设会造成闲置的固定预留比例。这是容量分配偏好，不是每个分组独享的配额或绝对防挤占保证。

例如四个同档、同优先级、同并发余量的 OAuth 账号分别绑定 5、5、5、2 个组时，权重比为 1:1:1:2.5。绑定两个组的账号期望分到约 45.5%，其余各约 18.2%；实时负载、额度和评分变化会改变比例。抽样按会话/请求锚点生成，不新增共享计数器；使用指数竞争排序，复杂度为 O(n log n)。

## 刷新与回退

配置按实例异步缓存，通常约 5 秒观察到其他实例的配置更新；本实例保存后立即生效。请求线程不执行历史聚合。统计按候选账号集合、分组、模型及窗口缓存，30 秒刷新，最多保留 32 个池、同时进行 2 次后台查询，单次查询限时 2 秒、最多 2000 个候选账号。

冷启动、查询失败、统计超过 1 分钟或超出资源上限时，仍按实时容量分流；不可用的历史信号按未知处理，不恢复旧 Top-K，也不把未知质量当成已验证通过。统计就绪后补入质量、延迟和收益信号。不会因此发送主动探测请求；质量运维可独立补充质量样本。

## 延迟惩罚与恢复探索

`latency_penalty_minutes` 配置延迟降档时长，默认 **10 分钟**，允许 **0–1440 分钟**；0 保留原有持续降档行为。P90 和首 Token 目标不变，不以降低统计分位数掩盖慢请求。

达到最小样本数且同组同模型 P90 超过目标时，惩罚截止时间为最近一次超过目标的有效首 Token 用量记录创建时间加配置时长。有效样本仍要求流式、首 Token 时间为正且有实际用量或费用；失败占位、非流式、无首 Token 时间、其他组/模型的请求均不会延长期限。反复刷新评分、重启实例或读取同一批旧历史不会重新开始计时。惩罚期内继续降档，但保留原有溢出路径；惩罚不是账号禁用。

到期后，延迟超标本身不再持续压到降档池，而转入“等待恢复样本”的数据不足档。质量通过率达标、最新质量检测通过、实时负载已知且低于配置上限，并无近期错误、历史亏损或拥堵风险时，账号可参与现有 **10% 探索概率**。冷启动与恢复账号共用这一机会，不额外叠加 10%；同一显式优先级、容量档与协议约束继续生效。正常档仍优先，恢复账号保留 P90 的评分和分流权重惩罚，便宜或并发上限高也不能直接抢占正常档的大比例流量。

新的有效慢样本使仍超标的 P90 重新进入惩罚期；P90 达标则立即回到正常档。该机制提供重新取样机会，不保证每个账号固定请求数或在某个时刻一定恢复。粘性/任务归属、OAuth 额度优先、模型准入、真正的限流/冷却及利润门仍可限制恢复流量，不会发送额外付费探测请求。

管理员页面增加惩罚时长与说明，候选表展示惩罚截止及恢复状态。配置/API 为加法变更，旧存储缺字段取默认 10 分钟，旧客户端保存时保留当前值；显式 0 可退回旧行为。无需数据库迁移，历史用量不改写；回退旧二进制将忽略新字段并恢复持续降档。候选快照仍使用最近一次路由观察到的配置与负载，读取快照只重算评分，不代表已分配新流量。

## 近期上游 attempt 错误率

现有高级调度已经使用账号级进程内 EWMA 错误信号（单次权重 0.2、空闲半衰期 2 分钟），原优先调度也会乘以 `1 − EWMA`，并将超过 20% 的账号标为风险。这次新增的是可配置、按公开请求模型/精确分组/入站端点隔离的 HTTP attempt 统计，不通过两条错误日志推算账号或供应商故障。

本页新增三个设置，仍保存在 `priority_scheduling_v1`：

| 字段 | 新配置默认值 | 范围 | 含义 |
| --- | --- | --- | --- |
| `error_rate_weight` | 25 | 0–100 | 独立错误惩罚强度，不重分配原四项预设或自定义权重 |
| `error_rate_window_minutes` | 10 | 1–60 | 最近分钟桶数量，包含当前分钟 |
| `error_rate_prior_samples` | 5 | 1–1000 | 平滑先验，相当于这些成功样本 |

对同一账号、公开请求模型、精确分组及逻辑入站端点，在窗口内记成功 `S`、失败 `F`。最近实际选号快照的错误率证据显示失败数/有效尝试总数（`F/(S+F)`）、百分比；有效样本少于先验时标注“样本不足”，完全没有样本时显示“无尝试样本”而不是 0%。列内同时标注错误统计读取时刻和窗口分钟数，读取时刻是本次刷新快照读取实时证据的时钟，不代表当时实际选路。实际用于评分的平滑值为 `F/(S+F+prior)`；乘数为 `max(0.1, 1 − error_rate_weight/100 × 平滑值)`。最终得分＝原质量/延迟/并发/成本四项加权基础得分 × 乘数。默认先验下，只有一次失败的平滑值是 1/6，默认错误权重对应乘数约 0.958；不会因为第一条错误就将新号打入不可恢复的错误风险档。

正权重**替换**原优先调度账号级 EWMA 乘数和错误风险降档，不再叠乘。错误率只软降分，在既有容量/质量体验档和管理员优先级相同的候选中，低错误率获得更大的抽样权重；高错误率候选仍有非零权重和抢槽兜底机会。不会借此跨越管理员优先级、质量/利润硬门槛、禁用/限流状态或硬会话所有权。已有质量、延迟、拥堵及亏损规则仍可能先于错误得分排序。高错误率不能通过新号/延迟恢复探索通道插队，也不能提供 OAuth 后备预算；窗口到期后这些错误限制自然消退。

已有持久配置没有 `error_rate_weight` 字段时按 **0** 加载；只有全新配置使用 25。旧客户端保存时省略这三个字段，服务器保留当前值。零权重恢复此前账号级 EWMA 惩罚；关闭整个优先调度恢复原来的调度开关行为。参数范围校验拒绝非有限权重及无效窗口/先验，无需数据库迁移。

### 统计单位和归属

每次真正进入原生 HTTP/插件、SIWC 或 BPS HTTP 发送调用，创建独立的 attempt 观察者。所有内部同账号重试、BPS 修复请求和换号后的发送分别观察。收到的响应体只有一个统计所有者，重复关闭只结算一次；handler、健康观察器、熔断和日志反馈不写这组计数。因此账号 A 的失败不会被账号 B 最终成功覆盖，也不会因同一错误经过多层转译而重复计数。请求预检、取令牌、RPM/代理租约准入及本地存储失败不生成样本。

键是账号 ID＋**客户端公开请求模型**＋精确分组（包括无分组）＋实际入站端点（`/v1/responses`、legacy `/v1/responses/compact`、`/v1/chat/completions`、兼容 Messages 入口）。入口与兼容能力独立：普通 Responses 即使用 CC 能力或上游 Chat 转换，仍读写 Responses 的桶。channel/composite 改写之前保存公开模型；路由模型继续用于能力和账号映射，质量探测按账号与路由模型读取。转发模型目标会去除边缘空白，渠道计费字段与金额计算保持原口径。不同公开别名、分组及入口不共享 attempt；账号映射和内部重试仍归属原请求身份，不用响应模型重新归因。升级后进程内 attempt 重新积累，不读取旧路由键来凑样本。

| 证据 | 结果 |
| --- | --- |
| 上游 429（普通速率限制）、容量降载、408/5xx、可识别的网络错误或上游 watchdog 超时 | 失败；现有冷却/健康熔断照常独立生效，不额外延长其时长 |
| HTTP 200 的 `response.failed` / `error`，或 SSE 在正常终止前 EOF/读失败 | 失败，HTTP 状态不决定业务成功 |
| Responses 成功终止事件、Chat 的 `[DONE]` / finish_reason / usage 终止条件，且没有应用错误/下游断开 | 成功 |
| 完整有效的非流 JSON 成功响应 | 成功；仍在进行中的 response 不算完成 |
| 客户端取消、下游断开、无效输入、`user_inactive`、鉴权/权限/余额或业务配额拒绝 | 排除，既不加成功也不加失败 |
| 本地准入/内部存储错误、未识别的传输错误、不完整或超出观察上限的 JSON/SSE 证据 | 无样本，排除分母 |

响应观察器不修改响应、不新增重试、不改变已开始流的故障转移语义。最终一次样本等转发返回后确认 `ClientDisconnect`；下一次内部发送前先结算上一次。明确的上游首输出 watchdog 与客户端取消分开处理。上游 `Tool arguments stopped making progress: consecutive whitespace outside JSON strings (output_index=1, whitespace_bytes=1024, limit_bytes=1024)` 属于测试覆盖的应用错误样例：本基线未找到该 guard 的本地生成点，收到 502 或 HTTP 200 流内失败都会计入对应 attempt，未调整任何 guard 阈值。

### 有界状态和实例边界

复用 `openAIAccountRuntimeStats` 的进程内运行时容器，用 mutex 保护至多 4096 个作用域键，每键固定 60 个分钟桶。每次写入为常数操作；读取最多汇总 60 个桶，不在请求热路径查询 SQL 或扫描 ops 日志。键满时按固定环替换，淘汰后的证据为未知；重启清空。分钟桶在边界整体到期，窗口精度为分钟，例如 10 个桶的实际覆盖长度介于约 9 和 10 分钟，旧错误不会被刷新评分续期。

**这不是多实例一致的全局成功率。** 现有 EWMA 就是本地机制，新统计沿用该边界；每个实例只知道自己承接的 attempt，负载均衡、实例重启或缓存淘汰会导致不同证据。区域候选同步不会复制这些桶，没有新建 Redis/SQL 全局统计服务。

新增采集覆盖上述真实 HTTP 发送点；WebSocket、浏览器/自定义非 HTTP 通道及未经过这些发送点的子请求不伪造 HTTP 样本。正权重下没有对应 HTTP 证据时错误项为中性，既有通用健康反馈、粘性安全策略和冷却/熔断仍运行。需要全局或这些通道的 attempt 质量时，须另行接入明确的发送/终止生命周期，不能从 handler 最终成功或 ops 日志补分母。

被动响应观察每次最多保留 64 KiB JSON 或一条 SSE 行；超限/无法解析的证据保守排除，长单事件响应因此可能没有样本，不能把窗口覆盖率当成全部流量覆盖率。观察内容不进入 runtime 状态或新日志，状态仅保存模型/端点及计数。候选评分表错误率列显示当前实例、模型/端点、窗口、失败数/有效尝试总数、百分比、样本不足/无样本态、错误统计读取时刻、基础得分、错误乘数和最终得分。读取时刻只描述刷新时读取实时证据的时钟；候选账号、配置和负载仍取自原选号快照，重算与历史刷新不会伪造当时实际路由。零权重时乘数来自旧 EWMA，应结合配置解读。候选分数和抽样权重仍不代表实际选中记录或全局分配概率。

## 完成后的样本刷新与普通粘性

首 token 在流内测量，但历史样本只在 Forward 收尾并持久化用量后成立。本次不写入流中临时样本，不改变用量提交或计费链路。公开 `requested_model` 与精确分组用于读取延迟、体验和收益；质量使用独立路由模型，缓存同时区分公开/路由模型与配置版本。缺失首 token 仍计入 unknown；查询失败或 reader 未返回的账号不会伪装成已读到零样本。

完成查询后，有效用量证据不足最低样本数的 scope 采用 5 秒缓存，成熟 scope 仍为 30 秒。全实例任意 1 秒窗口最多启动 2 次异步查询（允许两次突发）、并行最多 2 个，单次 deadline 2 秒，最多 32 个 scope、每 scope 2000 个账号；失败保留近期证据并按原 5 秒冷却重试，超过 2 分钟不再当作可用历史。持续有同 scope 触发且 SQL 成功时，已完成持久化的新号用量无需再发付费请求即可由页面刷新带入；排队、数据库失败和 scope 竞争仍可能延后，5 秒不是端到端 SLA。

页面保留最多 3 次 1 秒快速跟读，之后每 5 秒读取最近快照；已 ready 的空历史也继续刷新。单页仅一个定时器和一个在途请求，隐藏页暂停读取，接口失败后按 15 秒退避，卸载或退出立即停止。刷新只推进历史/评分读取时间，不伪造新选号或新负载时间。

“延迟优先调度”软模式下，普通 session hash 快速复用会读取同 scope 的有效测量证据；存在 `latency_above_target` 时，本回合进入已有评分与安全选号流程，保留原绑定。此判断独立于可选 EWMA/容量 escape 开关；加权 sticky 的后备捷径也不能重新引入活动惩罚，容量逃逸不会主动偏向已知慢备选。完整评分池仍保留慢账号作为最终可用容量，不全局禁用账号或模型。仅 sticky 的流量也能启动有界异步历史读取；缺样本不视为慢。

provider-bound `previous_response_id`、guardian/task ownership、禁止逃逸及加密推理亲和仍保留归属，不因慢而直接换 key、删 ID 或重放对话。软模式保留原复用；停止模式按下一节对原 owner 应用相同的受限兜底准入。本次判断只发生在发送前，不增加输出后的重试授权。现有 `latency_penalty_minutes` 含义不变：默认 10 分钟；0 保持持续降档；缺失坏样本时间不虚构截止；真正的新慢样本可续期，读旧历史不能续期，到期允许普通 sticky 恢复。该保护属于请求范围评分，仍受样本门槛、当前分位与可用历史约束。

### 两种延迟惩罚方式

`latency_penalty_mode` 可选择 `deprioritize`（“延迟优先调度”）或 `stop`（“停止调度”）。旧配置缺字段默认 `deprioritize`，旧客户端保存时省略字段会保留服务器当前方式。两者共用现有 `latency_penalty_minutes`（默认 10 分钟）和相同的有效样本、分位、目标与最近慢样本触发条件，不新增两倍目标门槛。

软模式保留原有降档、容量比较和最后后备。停止模式保留精确账号 × 公开模型 × 路由模型 × 分组的惩罚，但用户明确授权在全池停调时“根据延迟启动最低档 2–5 个账号”。这属于请求范围的可用性兜底，不清除惩罚，也不改变账号状态。

先应用当前请求的其它硬性资格：分组、平台、模型/能力/transport、管理员启停、隐私、认证状态、配额/RPM、ticket、安全隔离、母账号、利润控制及路由排除。只有这些资格均满足的账号进入延迟比较；不能用不符合资格的健康账号阻止兜底，也不能用兜底放行其它资格不满足的账号。真实认证、预发送权威状态、配额及并发检查仍独立执行。

具体人数与分档算法（不增加测量门槛）：

1. 使用 `scorePriorityCandidate` 已验证的 `SelectedTTFTMs`，沿用配置的分位、测量口径、最低样本数及 legacy P90 兼容规则。有效测量且无活动延迟惩罚的候选优先；只要存在，就不开放受罚或未知候选。
2. 没有上述健康候选时，有效测量按延迟从低到高排序；相同指标值为同一档，取最低档。最低档人数为 k，则开放 `min(实际池人数, 5, max(2, k))` 个。最低档只有 1 个时补入下一低延迟账号；同档超过 5 个按账号 ID 升序截断。现有 eligible/insufficient/degraded 档位混合质量、负载和成本，不能充当纯延迟档位，因此采用指标相同值分档，不发明毫秒边界或倍数门槛。
3. 历史 pending/error/unavailable、空历史、样本不足或测量口径不匹配均保持未知。未知排在所有有效测量之后，只有有效测量不足人数下限时才补入。全池未知是一个未知档，按账号 ID 升序最多开放 5 个；仅 1 个用 1 个。不把未知标成最快或慢，不补零或写假样本。异步历史查询、冷却和缓存上限保持不变。
4. 单次选号冻结原候选范围；首次进入兜底时固定开放集合（包括等待期间最后一个健康候选变慢），覆盖选路、sticky/weighted fallback、等待计划、slot 后及首次 generation 写入前。复检可以收紧兜底集合，不能重新补入第 6 个受罚/未知账号或越过原 scope。原资格池中恢复健康的账号仍优先参与，不占用或扩大受罚兜底人数。新请求/新 WS turn 重新计算；不能靠重复准入检查无限扩池。

切换软/停止方式复用同范围测量缓存；配置方式不改变测量样本。惩罚 deadline 原样保留，0 分钟持续保留惩罚且仍适用上述兜底。provider-bound previous_response_id（包括已被路由排除的 owner）、guardian/task、加密亲和或禁止迁移的归属只能在原账号满足同一准入规则时继续；否则返回暂不可用，保留 sticky、响应 ID 和状态，不触发换账号或重放。HTTP 提供 Retry-After: 5，WS 使用可重试关闭与 5 秒提示。

只在新请求/新 WS turn 发送前校验。generation 已尝试写入或已有输出时，不因新惩罚中断、换 owner 或重放。到期恢复和可用性兜底均不解除权限、额度、安全冷却或管理员状态。停止模式不改账号 status/schedulable、费用、账本或历史用量。

### 发送前等待与惩罚时钟

native WS 的 ctx_pool/shared/dedicated 在获取连接租约、握手及发送前准备完成后，对尚未写入上游的新 generation 再检查停止准入。等待期间新生效的停止不会越过这道检查；已尝试写入的同回合继续沿用原有重试与输出保护，不因新惩罚中断、改 owner 或重放。普通选号后段遇到晚到停止时仍尝试健康备选；全部候选和等待计划穷尽后返回专用延迟暂不可用原因与重试提示，保留此前供应商错误只作历史诊断。

惩罚截止仍为 `latest_bad_latency_at + latency_penalty_minutes`。`latest_bad_latency_at` 来自有效慢用量行的 `created_at`，不是页面或 history 读取时间。首 token 测得后须等流收尾和用量记录才有持久历史；用量创建后到 SQL/cache/UI 可见的延后会消耗剩余期限。例如记录时间后第 8 分钟才读到该行，10 分钟惩罚只剩 2 分钟，读取不会重启十分钟。流中不写临时样本；该边界没有在本次改成按可见时间续期，也不承诺首 token 起立即生效或“页面看到后再保护十分钟”。
