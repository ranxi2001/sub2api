# 加密 agent 历史账号策略

默认仍按已登记的账号和原生 Responses 路线恢复加密 `agent_message`。原账号限流或过载时，保留原等待提示和恢复时间。管理员可显式允许完整历史尝试普通账号池中的其他合格账号：

```yaml
gateway:
  disable_encrypted_agent_owner_binding: false
```

环境变量 `GATEWAY_DISABLE_ENCRYPTED_AGENT_OWNER_BINDING=true` 优先于 YAML；未配置或 `false` 为严格模式。Compose 模板透传此变量。它是进程启动配置，没有后台 UI 或逐请求覆盖接口。

开启后，已完成交付的 agent 历史不会仅因原账号/路线绑定阻止选择 B。网关保留原始历史、密文和工具结果，通过普通身份、用户及 Key 权限、分组、模型、余额、额度、账号状态和并发准入后才尝试发送。没有合格账号仍返回错误。原账号的服务端 `previous_response_id` 不是可移植历史：指针归属未知或属于其他账号时，仍明确拒绝。当前请求或现有 WS 连接已经观察过的 owner 记录丢失，也必须拒绝，不能用预热帧补造当前历史。请从客户端提供完整原历史，不要删除密文或工具结果来续接。

跨账号的密文兼容由上游决定。本开关不保证上游接受、无损续接或费用不变。上游拒绝时保留原错误处理；不能通过删除消息、重放连接首帧或把已执行工具结果再次自动提交来伪造成功。网络中断、客户端取消和未确定交付的请求也不能据此自动重放。

## Redis 与切换流程

无需迁移数据库或清空 Redis。已完成的 A 输入记录保留原 producer，不会因为被 B 消费就改成 B 或制造 A/B conflict。B 新生成的密文输出仍先建立 pending 屏障，仅在成功的最终下游写之后提交 B；失败、未确定交付、存储错误和现有 conflict 继续保守拒绝。原有 TTL 仍生效。新请求首次遇到的历史若已过期或没有 owner 记录，无法推断被遗忘的原账号；沿用普通准入并不构成已交付或密文兼容的证明，也不授权自动重放。它与当前请求/连接已知记录随后丢失的明确拒绝不同。

1. 先保存客户端当前完整历史，停止接入新请求，等待在途请求结束并排空旧 WS 连接。
2. 在所有共享该 Redis 的网关节点配置相同值，按正常配置流程重建/重启进程。
3. 恢复流量，客户端重连 WS，再提交完整当前历史。不能把连接初始预热帧当作后续轮历史。

不要混跑 true/false 节点或将旧 WS 无条件保留到新策略中。进程持有启动配置，旧节点仍会严格拒绝；旧版本的消费发布行为还可能产生冲突，因此不承诺无条件滚动切换。

回到 `false` 同样需要所有节点统一配置、排空连接和正常重启。只有 A 记录的历史恢复严格绑定 A；同时含 A 和 B 已完成输出的历史会明确拒绝为混合归属，不能伪造成单一 owner。回退二进制也有这个限制，清 Redis 不是安全恢复手段。

## 验证边界

Issue805 回归夹具使用隔离的真实 Redis、虚构密文和真实 localhost HTTP/WS 网络连接，包含 HTTP JSON/SSE、WS `ctx_pool`、`passthrough` 和 `http_bridge` 场景。实际执行结果以对应提交的 GitHub CI 日志为准。即使合成上游接受 B，也只证明策略与发送行为，不证明真实供应商的跨账号加密兼容；不需要调用付费上游或读取生产凭据。
