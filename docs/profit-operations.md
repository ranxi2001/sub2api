# 利润运营与独立上游渠道归属

利润运维页 `/admin/profit-operations` 按渠道显示本站请求的收入、成本、毛利润和毛利率。在「服务商管理」添加供应商后，无须再手建同名渠道；原有手工渠道仍可用。筛选和下钻使用渠道内部 ID，不按显示名称识别。

例如周一开始手填 A 的网址和 Key、周五才登记 A：重新查询含周一的时段，原网址行里没有其他明确归属的请求会归入 A，不需要重新导入 Key，也不会在两行重复计数。这是报表分组，不改账号路由和历史用量。没有逐笔历史网址时，用原网址行的当前有效配置来认领；明确的历史归属和解绑优先。只有唯一的 HTTPS 站点根地址或其 `/v1` API 地址参与认领，不把其他租户路径、动态或无法确定的地址并成同一站。

`/admin/upstream-channels` 管理实体与分页成员；账户管理支持创建时绑定、编辑、批量选择。一次绑定最多 100 个明确账号，页面展示受影响账号并要求确认，写入使用 revision CAS 后 GET 读回。修改渠道成员会递增渠道 revision，旧确认失效。

删除有成员的渠道一律冲突。管理员须先在成员页明确选中有界账号并确认解绑、重新读取版本后，才可删除空渠道。关联表外键禁止渠道级联删除；解绑只改变当前归属，不修改账号路由、历史 usage 或账本。软删除账号保留绑定与历史请求归属；真正物理删除时仅清除其绑定，migration 313 触发器推进原渠道 revision。目录、成员、质量和容量描述当前配置。财务事件优先使用冻结证据，再看事件当时的手工或导入归属；缺乏同期记录的旧手工渠道仅作兼容估算。

## 财务口径

- **已绑定供应商：**上游成本为匹配到本站请求的上游用量账单 `actual_cost`（本地账单表的 `amount`）。不使用服务商钱包总消费、余额扣款凭据或本站倍率。若只匹配部分请求，显示匹配笔数；不能用倍率补差或把部分小计当作整段成本。
- **未绑定供应商：**包括只有手工渠道 ID 的渠道。估算成本 = 保存的 `usage_logs.total_cost` × 当前账号成本倍率 `extra.cost_multiplier`；未设置倍率时用 0.1。显式零倍率与缺少有效倍率不是一回事。
- **两种渠道：**请求收入取本站已保存的 `usage_logs.actual_cost`，订阅计价不等于现金收入。毛利润 = 收入 − 成本，毛利率 = 毛利润 ÷ 收入。明确的零价按零算，收入为零时不显示百分比。跨渠道合计先按各自口径计成本，再按总收入算毛利率，不平均每行百分比。

## 服务商对账与隔离试用

仅在测试实例上从源码构建此分支；使用独立的 PostgreSQL、缓存、模拟上游及虚构 Key，不要指向生产服务。先保留测试库副本，再按项目正常启动流程应用迁移 383–386；回退测试环境请恢复副本，不要手工删除业务表。只打开利润页会读本地保存的数据，不会向服务商发请求。成功同步写入的账单会一直保留，再次打开同一时段直接使用，不会按时间删除，也不会在进入页面时自动重新拉取。离线用例通过模拟 HTTP 传输提供上游响应；管理页面的实际连接仍要求受控的公网 HTTPS 测试站，不能用 localhost，也不要为试用关闭地址校验。

1. 给手填网址和 Key 的测试账号记两笔虚构请求，再在服务商管理添加同网址的 A。选择含这两笔请求的日期，确认两笔只出现在 A 下；不更动账号，也不等下一笔请求。
2. 在上游维度应用日期后，用 A 行的账单同步按钮。支持的 Sub2API 上游通过登录用户的用量接口完整读取覆盖区间的 UTC 日历页，再按 `[from, until)` 匹配本站请求。打开报表本身不触发同步。New API 没有这条逐笔同步路径，明确的 Simple Mode 也不作为上游计费数据源。
3. 登记日期不是查询起点。读到上游记录后，手填账号须有可核实的上游请求标识，才能把该笔消费与本站请求对应；不按接近的时间或金额猜测，也不因网址一致就把共享钱包或共享 Key 的全部消费算给本站。没有可用标识的历史请求可归到 A，但不会生成一笔虚构成本。

   点击同步后可以离开页面。超过 5,000 笔会自动分批：上游每页 250 笔，换会话时复核用户和分页位置；读完整个覆盖范围后，数据库按每批 512 笔逐笔匹配，在同一事务内提交。最后一页读取失败或最后一批与已存金额冲突，都不会留下半份新账。重复同步相同账单不会增加笔数或金额。

   同一实例、同一服务商、同一时段重复发起时复用正在运行的任务。每个实例最多同时处理两个服务商，同一服务商同一时间只处理一个时段。单任务最长 30 分钟，去重索引和候选账单有 96 MiB 的估算内存预算（不是记录数上限）。多实例部署需将状态查询发往启动任务的实例；实例重启或任务完成一小时后，旧句柄可能返回 404，可先刷新报表，再决定是否重新同步。已经提交的账单不受影响。

   上游返回 HTTP 429 时，同一页会等待后重试，分页、换会话时的 `/api/v1/auth/me`、续读锚点，以及尚未读到任何页之前的登录，都按这条处理。响应带正的 `Retry-After`（秒数或未来的 HTTP 日期）时按其等待；否则从 2 秒起指数增加，上限 45 秒，并加不超过 250 毫秒的抖动。若下一次等待会超过该任务剩余的 30 分钟，失败原因为 `rate_limited`，不把没读完的扫描写成新账。日志记录限流、等待时间、重试次数和最终原因，不记录令牌、Cookie 或凭据。重试成功后继续翻页，整段读完才按原有每批 512 笔在同一事务内对账；完整性校验不因限流放宽。本地时段跨两个 UTC 日时仍是一次扫描：后面的记录仍可能使前面的候选作废，因此不会把已经读完的前一个 UTC 日单独入账。

   成功同步会记下该时段的完成时间。报表只读已保存账单和这个时间，打开页面或刷新快照不会向上游发请求。已绑定的 Sub2API 行显示最近成功同步时间，并说明当前用的是已保存账单；此时段还没有成功同步、也没有已保存账单时会说明，仍由操作者点击「同步上游账单」。重复同步同一账单仍不重复计数。
4. 验收例：本站两笔收入合计 100，上游用量明细为 32 和 13，即使另有余额实扣 30 和 10、共享钱包显示 60，主表也应为 **成本 45、毛利润 55、毛利率 55%**。重复同步不得翻倍；只匹配到 32 时应为 1/2，不显示整段利润。另一个未绑定供应商的手工渠道仍按倍率估算。

测试数据不要用真实客户请求标识、令牌、站点地址或钱包截图。原版利润运维的验收记录见 [PROGRESS.md](../PROGRESS.md)。

## 大数据量查询

利润快照的服务端查询预算为 5 分钟，页面等待上限为 5 分 30 秒，独立于其他管理接口的默认超时。等待期间页面保持汇总状态；切换查询或离开页面仍会取消旧请求。反向代理的读取超时应至少为 330 秒，避免先于应用中断响应。

统计只投影计算所需的用量字段，保留完整时间范围、精确合计和延迟分位数。分页仍只限制展示条数，不截断统计样本。超出查询预算时接口返回 HTTP 504 和 `PROFIT_OPERATIONS_TIMEOUT`，页面明确显示统计超时，不将未完成结果显示为零。
