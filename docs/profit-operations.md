# 利润运营与独立上游渠道归属

利润运维页 `/admin/profit-operations` 按渠道显示本站请求的收入、成本、毛利润和毛利率。在「服务商管理」添加供应商后，无须再手建同名渠道；原有手工渠道仍可用。筛选和下钻使用渠道内部 ID，不按显示名称识别。

例如周一开始手填 A 的网址和 Key、周五才登记 A：重新查询含周一的时段，原网址行里没有其他明确归属的请求会归入 A，不需要重新导入 Key，也不会在两行重复计数。这是报表分组，不改账号路由和历史用量。没有逐笔历史网址时，用原网址行的当前有效配置来认领；明确的历史归属和解绑优先。只有唯一的 HTTPS 站点根地址或其 `/v1` API 地址参与认领，不把其他租户路径、动态或无法确定的地址并成同一站。

`/admin/upstream-channels` 管理实体与分页成员；账户管理支持创建时绑定、编辑、批量选择。一次绑定最多 100 个明确账号，页面展示受影响账号并要求确认，写入使用 revision CAS 后 GET 读回。修改渠道成员会递增渠道 revision，旧确认失效。

删除有成员的渠道一律冲突。管理员须先在成员页明确选中有界账号并确认解绑、重新读取版本后，才可删除空渠道。关联表外键禁止渠道级联删除；解绑只改变当前归属，不修改账号路由、历史 usage 或账本。软删除账号保留绑定与历史请求归属；真正物理删除时仅清除其绑定，migration 313 触发器推进原渠道 revision。目录、成员、质量和容量描述当前配置。财务事件优先使用冻结证据，再看事件当时的手工或导入归属；缺乏同期记录的旧手工渠道仅作兼容估算。

## 财务口径

- **已绑定供应商：**上游成本取渠道运维已经保存的「今日消费」（`mature_providers.metrics.today_spend`），也就是上游钱包的今日消费。这个数字可能包含不是本站产生的支出，仍然整笔使用，不按本站请求拆开，也不再用逐笔上游账单。币种沿用渠道运维保存的来源币种；只有 USD 才与本站请求收费相减。没有当天读数、读数不是该消费日，或币种不是 USD 时，成本显示不可用，不用倍率补上。
- **消费日：**渠道运维的「今日消费」只是当天的快照。New API 在刷新时请求 `/api/log/self/stat?type=2`，起点是北京时间当天 0 点。Sub2API 在刷新时请求 `/api/v1/usage/dashboard/stats`，优先取 `today_actual_cost`，否则 `today_cost`，币种记为 USD；上游自己用站点时区的当天 0 点起算（默认北京时间），快照里不另存时区。利润报表因此只在查询窗口是**北京时间当天**时使用该读数：窗口从当天 0 点开始，结束于当前时刻（允许约 5 分钟误差），并且 `observed_at` 也落在这一天。浏览器时区为北京时间时，页面上的「今天」就是这个窗口。查询接口不接受比现在晚超过 1 分钟的结束时间。昨天、上周、近 24 小时或其他自定义区间不套用这个数字。
- **下钻：**按账号或模型比较，或筛选账号、分组、模型时，不把钱包总额按比例分到每一行。钱包成本留在渠道合计；这些子集的上游成本显示不可用。
- **未绑定供应商：**包括只有手工渠道 ID、没有钱包今日消费的渠道。估算成本 = 保存的 `usage_logs.total_cost` × 当前账号成本倍率 `extra.cost_multiplier`；未设置倍率时用 0.1。显式零倍率与缺少有效倍率不是一回事。
- **两种渠道：**请求收入取本站已保存的 `usage_logs.actual_cost`，订阅计价不等于现金收入。毛利润 = 收入 − 成本，毛利率 = 毛利润 ÷ 收入。明确的零价按零算，收入为零时不显示百分比。跨渠道合计先按各自口径计成本，再按总收入算毛利率，不平均每行百分比。同一天里，已绑定渠道用各自的今日消费，未绑定渠道用倍率估算，再相加。

打开利润页只读本地保存的渠道读数和本站请求，不会为了这份成本去翻上游 `/api/v1/usage`，也不会自动刷新服务商。要更新「今日消费」，仍在渠道运维里刷新该服务商。页面不再提供「同步上游账单」。旧的逐笔同步代码可以留在仓库里，但不再决定本报表的成本。

## 服务商对账与隔离试用

仅在测试实例上从源码构建此分支；使用独立的 PostgreSQL、缓存、模拟上游及虚构 Key，不要指向生产服务。先保留测试库副本，再按项目正常启动流程应用迁移 383–386；回退测试环境请恢复副本，不要手工删除业务表。只打开利润页会读本地保存的数据，不会向服务商发请求。离线用例通过模拟 HTTP 传输提供上游响应；管理页面的实际连接仍要求受控的公网 HTTPS 测试站，不能用 localhost，也不要为试用关闭地址校验。

1. 给手填网址和 Key 的测试账号记两笔虚构请求，再在服务商管理添加同网址的 A。选择含这两笔请求的日期，确认两笔只出现在 A 下；不更动账号，也不等下一笔请求。
2. 在渠道运维刷新 A，使目录里记下当天的「今日消费」。利润窗口选北京时间当天后，A 的上游成本等于这个数字，即使另有逐笔账单或共享钱包里的其他支出。窗口换成昨天或任意其他区间时，成本不可用，不能把今天的数字填进去。
3. 登记日期不是查询起点。没有逐笔请求标识的历史请求仍可归到 A，但不会因此生成一笔虚构的逐笔成本。按账号或模型下钻时，渠道合计仍是整笔今日消费，每一行不显示分摊金额。

验收例：本站两笔收入合计 100，渠道运维「今日消费」为 60 USD，且读数属于北京时间当天。即使上游用量明细是 32 和 13、另有余额实扣，主表也应为 **成本 60、毛利润 40、毛利率 40%**。同一钱包不会按两笔请求各计一次。另一个未绑定供应商的手工渠道仍按倍率估算；和 A 加总时，成本是 60 加上该渠道的估算。今日消费为 0 时成本是 0，而不是不可用。

测试数据不要用真实客户请求标识、令牌、站点地址或钱包截图。原版利润运维的验收记录见 [PROGRESS.md](../PROGRESS.md)。

## 大数据量查询

利润快照的服务端查询预算为 5 分钟，页面等待上限为 5 分 30 秒，独立于其他管理接口的默认超时。等待期间页面保持汇总状态；切换查询或离开页面仍会取消旧请求。反向代理的读取超时应至少为 330 秒，避免先于应用中断响应。

统计只投影计算所需的用量字段，保留完整时间范围、精确合计和延迟分位数。分页仍只限制展示条数，不截断统计样本。超出查询预算时接口返回 HTTP 504 和 `PROFIT_OPERATIONS_TIMEOUT`，页面明确显示统计超时，不将未完成结果显示为零。
