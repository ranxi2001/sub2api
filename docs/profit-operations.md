# 利润运营与独立上游渠道归属

利润运营页 `/admin/profit-operations` 按上游渠道展示本站请求的收入、估算成本和有扣款凭证的成本。服务商管理接入的站点会得到独立渠道，无需再手工按名称创建；原有手工渠道继续可用。渠道内部 ID 和 code 不随显示名称变化。

账号归属不由 URL 派生。同一渠道可包含不同 URL、无效/未知 URL、动态 OAuth 或不支持读取 URL 的账号；不同渠道也可包含相同 URL。只有当前未绑定账号才按现有安全有效 URL 自动聚合，无法识别时保留 unknown。利润筛选与下钻使用实体内部 ID，不受 URL、名称和分页位置变化影响。

`/admin/upstream-channels` 管理实体与分页成员；账户管理支持创建时绑定、编辑、批量选择。一次绑定最多 100 个明确账号，页面展示受影响账号并要求确认，写入使用 revision CAS 后 GET 读回。修改渠道成员会递增渠道 revision，旧确认失效。

删除有成员的渠道一律冲突。管理员须先在成员页明确选中有界账号并确认解绑、重新读取版本后，才可删除空渠道。关联表外键禁止渠道级联删除；解绑只改变当前归属，不修改账号路由、历史 usage 或账本。软删除账号保留绑定与历史请求归属；真正物理删除时仅清除其绑定，migration 313 触发器推进原渠道 revision。目录、成员、质量和容量描述当前配置。财务事件优先使用冻结证据，再看事件当时的手工或导入归属；缺乏同期记录的旧手工渠道仅作兼容估算。

## 财务口径

估算成本 = 保存的 `usage_logs.total_cost` × 当前账号统一成本倍率 `extra.cost_multiplier`；未保存时沿用既有调度默认 0.1。请求收入 = 已保存 `actual_cost`；估算利润 = 收入 − 估算成本。账号扣费倍率、模型价卡成本和账本结算不再叠加。代码不改变该利润公式。

标准收费基数与收入均按历史保存值展示，不按当前价卡重算。订阅计价不等于现金收入；未知 URL/动态路由不虚构归属。若缺少有效金额/倍率，汇总按既有逻辑显示未知。

Migration 312 创建 `upstream_channels` 与 `upstream_channel_bindings`；不按 URL、展示名称或历史 usage 猜测实体关系。早期分支中的 URL-key 备注表、API 和 UI 已从本 PR 删除，因此 URL 只用于未绑定账号的只读自动归类，不是可编辑渠道身份。

## 服务商对账与隔离试用

仅在测试实例上从源码构建此分支；使用独立的 PostgreSQL、缓存、模拟上游及虚构 Key，不要指向生产服务。先保留测试库副本，再按项目正常启动流程应用迁移 383–385；回退测试环境请恢复副本，不要手工删除业务表。只打开利润页会读本地保存的数据，不会向服务商发请求。离线用例通过模拟 HTTP 传输提供上游响应；管理页面的实际连接仍要求受控的公网 HTTPS 测试站，不能用 localhost，也不要为试用关闭地址校验。

升级前导入、没有可核实钱包版本的 Key 不会被自动算到当前服务商，即使地址和 Key 编号相同。原账号继续转发，已有手工渠道绑定保留；要建立可用于对账的来源，请从当前服务商重新导入，自新导入生效起统计，不追认旧账。以后把服务商连到旧手工渠道，也不会改变该渠道迁移前的估算收入。

1. 在服务商管理接入一个测试服务商并导入 Key，打开利润运维。即使没有本站请求，也应看到该服务商的钱包行；缺少读数显示未知，不显示为零。旧手工渠道继续可用。改关联时核对新旧渠道并确认，已冻结的历史成本不随之移动。
2. 钱包行的今日/累计消费按该站点单位和最后观察时间展示，不跟随报表日期筛选，可能含其他系统、Key 或改绑前的消费。New API 只展示钱包，不支持逐笔同步。
3. 逐笔对账使用普通 HTTP 调用。两端都运行支持本功能的 Sub2API 时，上游以 `X-Sub2api-Usage-Id` 返回关联标识，并为升级后符合条件的余额扣款保存凭证。标识不是付款证明，旧账不回填。显式配置的响应头优先；WebSocket、截断或有歧义的标识不据此认账。
4. 选择并应用报表日期，再点测试服务商的同步按钮。读取覆盖区间的 UTC 日历页，在本地按 `[from, until)` 匹配；返回的匹配/未匹配笔数是本站请求，不是整个钱包。明确的 Simple Mode 不支持同步。旧站缺少证明接口时，有唯一用量匹配也只显示上游计价；鉴权错误或不完整分页不会作为成功保存。
5. 验收例：模拟本站两笔请求收入合计 100，对应上游余额凭证 30、10，另有同钱包外部消费 20。预期钱包读数 60、本站已对账成本 40、按请求收入计算的利润 60。再同步不得翻倍。如果只返回第一笔凭证，应显示部分成本 30、覆盖 1/2，整段成本和利润均未知；补齐另一笔后才显示 40 和 60。

测试数据不要用真实客户请求标识、令牌、站点地址或钱包截图。原版利润运维的验收记录见 [PROGRESS.md](../PROGRESS.md)。

## 大数据量查询

利润快照的服务端查询预算为 5 分钟，页面等待上限为 5 分 30 秒，独立于其他管理接口的默认超时。等待期间页面保持汇总状态；切换查询或离开页面仍会取消旧请求。反向代理的读取超时应至少为 330 秒，避免先于应用中断响应。

统计只投影计算所需的用量字段，保留完整时间范围、精确合计和延迟分位数。分页仍只限制展示条数，不截断统计样本。超出查询预算时接口返回 HTTP 504 和 `PROFIT_OPERATIONS_TIMEOUT`，页面明确显示统计超时，不将未完成结果显示为零。
