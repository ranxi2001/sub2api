# EasyPay 支付确认失败后的恢复

EasyPay 回调验签成功后仍会向该订单绑定的提供商实例二次查单。查询失败继续返回 HTTP 502，不凭回调中的成功状态直接充值。该改动解决查单暂时不可用后订单失去自动恢复机会的问题，不保证消除上游 EOF、超时或长期缺少查单接口的故障。

订单仍按原 `expires_at` 结束支付入口；`EXPIRED` 不代表已经确认上游未支付。现有到期 worker 在常规待支付查询之外，增加独立的 EasyPay 恢复阶段，每批最多查询 20 个到期 `PENDING` 或 `EXPIRED` 订单，每轮最多 15 秒。原常规查询与到期阶段各自的 30 秒预算保留；三个阶段合计上限 75 秒，仍受现有 3 分钟 leader 锁保护。某笔持续失败时按订单 ID 轮转，避免只重试最早一批；游标仅保存在进程内，重启或 leader 切换后从头扫描，不改变订单 `updated_at`。

恢复截止固定为原 `expires_at + 24 小时`。只有同一提供商实例查到已支付，并通过现有订单、商户、金额校验后，才进入既有幂等入账流程。查询失败、未支付、身份或金额不匹配均不充值，不在校验前改写交易号。自动恢复不会重新交付已取消、已退款或已完成订单，状态更新时也会重新检查，防止与管理员操作竞争。

超过截止时间后停止自动查询；之后的付款成功回调不会自动恢复订单余额，过期订单审计 `PAYMENT_AFTER_EXPIRY` 会注明需要人工对账。运营者应核对上游实际支付记录、原订单和余额入账记录，再使用既有管理流程处置，不通过反复修改 `updated_at`、重复下单或重放成功通知延长窗口。实际支付时间未由 EasyPay 查单协议可靠提供，因此窗口限制的是发现和恢复时间，不声称可以证明用户在到期前付款。

升级会自动检查仍在上述 24 小时窗口内的历史 EasyPay 到期订单。没有数据库迁移，不增加配置项；官方支付宝、微信及 BEpusdt 的恢复窗口保持原行为。无法识别历史提供商实例的旧订单继续拒绝猜测实例，需人工处理；上游始终没有可用查单接口的订单也不能自动入账。

窗口内的过期 EasyPay 订单继续占用现有“进行中订单”提供商保护：实例删除、禁用或受保护的商户配置修改会被拒绝，防止恢复期间丢失原查单身份。结算完成或超过恢复截止后释放该保护。

回滚旧二进制后，已经完成的入账和审计记录保留，不会自动撤销；旧版不再扫描过期 EasyPay 订单，并恢复旧版短恢复期。回滚前应先记录正在恢复窗口内的订单，安排人工对账，防止恢复机会随时间流逝。真实支付、生产部署和生产恢复效果需另行验收，离线回归不代表已完成这些验收。
