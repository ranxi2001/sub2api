# 持久化计费按用户合并

同一进程中，同一用户首笔已暂存事件立即结算；执行期间到达的事件进入该用户队列，下一轮最多合并 128 笔。复用上游批量结算的余额、Key 配额和账号额度合并计算，每笔仍保留独立用量、报价和持久化回执。每个用户最多排队 4096 笔，超过限制的事件留在持久化队列中等待恢复。

暂存、归属读取、结算、缓存确认及重试元数据共用数据库并发预算：最多 32，且不超过连接池上限的四分之一（至少 1）。同用户等待不占 SQL 连接；失败元数据更新只在已有或立即可取得预算时执行，不额外排队形成重试写入风暴。多进程的预算分别计算，账本行锁和去重表仍负责跨进程幂等。

批量事务同时提交去重、扣费、用量、报价和事件状态。SQL 失败整体回滚，保留事件供恢复；不会立即拆成 N 笔数据库重试。提交响应不确定时读取已存回执，无法确认则返回不确定结果，不再次请求模型或重放扣费。原有恢复 worker 继续逐项恢复，仍可隔离异常事件。

自动充值按批次最终余额检查一次，沿用原阈值、充值金额、未结清额度上限、账本和通知发件箱；本次充值由批次中最后一笔实际余额扣费标识，重放不会再次充值。不会为批次中每个中间余额单独产生充值。

没有新增配置或数据库迁移。已有 pending/applied/complete/legacy 事件继续兼容，旧二进制仍能读取新回执。此改动不能替代备份长快照治理、事件表归档和报表查询预算；没有生产压测数据，不能承诺具体吞吐提升。
